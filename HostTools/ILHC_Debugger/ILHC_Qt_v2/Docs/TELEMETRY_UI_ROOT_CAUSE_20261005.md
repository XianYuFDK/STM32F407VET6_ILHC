# 地图异常与低FPS：双端传输、解析与刷新修复

版本：PC v2.1.3；STM32本次EIDE构建。串口仍为115200 / 8N1。

## 已确认的原因与证据

用户截图显示19fps、Err 52512、参数快照回读超时。检查了当前运行程序的路径与启动时间，确认它运行的是本工程；不是打开了别处的旧副本。

1. 原底栏所谓fps统计的是接收遥测帧数，而绘制定时器设置为50ms，地图实际最多约20次/秒刷新。这两个指标混在一起，无法区分接收变慢与绘制变慢。
2. STM32普通文字应答优先发送，每条占用一个20ms位置数据时隙。只有轨迹应答做了交替，普通GET/ACK没有。提取真实`DebugUsart_Send`，在50个发送时隙加入31条普通回复，实际只发19帧位置，完整复现同样的频率。**截图没有原始串口记录，不能断言当时恰好有31条回复/秒**；这里证明了代码中的降频机制。
3. 旧JustFloat只有帧尾、没有帧头和校验。混合文字、丢字节或损坏后，payload中的`+inf`也等于帧尾，可能把错误字节组合成有限的假坐标。上一轮显示过滤无法保证排除连续坏帧，原运行判断还会接收到它们。Err是解析失步丢弃的字节数，不是GUI异常次数，也不等于UART硬件CRC错误数。
4. 在地图轨迹降采样中，简单`[::stride]`会跳过单个NaN断点，可能重新连接跳点前后的坐标。重复设置图元、状态样式也有可省去的刷新成本。

离线剖析中地图刷新函数本身耗时很短，没有证据把19Hz归因于显卡或地图规划。旧定时器设置和串口发送逻辑才是已复现的问题。

## 本次修复

- STM32增加`TELEM=1`选择CRC1位置帧。PC连接后自动协商，掉线/板复位后只重试传输协商，不重放运动指令。`VOFA`仍选择第三方JustFloat，旧固件可继续连接。
- CRC1每次DMA合并最多一条文字回复与一帧位置。回复不会再挤掉遥测。轨迹/普通回复有公平交替，持续TSTAT也不能饿死GET。忙时不改写在途缓冲，DMA提交成功才消费回复及推进序号。
- PC先验证CRC/序号，再向队列交付位置；拒绝损坏、重复/乱序和非有限OPS帧。进入CRC1后不再以payload帧尾降级解析。二进制payload也不再被扫描为GET文字，避免伪回读。原始缓存/录像及运行保护接收的是校验通过的数据，地图显示过滤保留作为实际定位跳变的显示隔离。
- 同一次read收到多帧时，按MCU毫秒时间恢复帧间间隔，避免全部拥有同一接收时间。坏包不刷新链路正常时间。
- 界面用20ms精确定时器刷新，分别显示“刷新xx Hz / 遥测xx Hz”；显示RX KB/s、CRC错误与序号丢包，提示里保留失步字节、无效定位及队列丢帧。旧固件显式显示“旧帧(无校验)”和失步字节数。
- 图标/目标坐标不变时跳过图元更新；样式状态不变时不反复polish。轨迹按缓存版本更新，降采样保留断点及相邻点，ZERO/跳变前后不会被缩减采样接成假青线。

没有改变坐标轴、车体尺寸、地图裕量、碰撞开关、轮使能、STOP及MCU运行保护。

## CRC1格式

固定112字节，小端序；回复文字仍为完整CRLF行，位于二进制帧之前。

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | `A5 5A 01 18`：协议标识/版本1/24通道 |
| 4 | 4 | uint32序号，成功提交DMA后递增 |
| 8 | 4 | uint32 MCU HAL毫秒时间 |
| 12 | 96 | 原24个float，通道、单位、轴序不变 |
| 108 | 4 | 前108字节的CRC32/IEEE，等同`zlib.crc32` |

位置仍为ch0/ch1的cm和ch2的deg。CRC覆盖二进制遥测，文字回复仍按完整行单独解析。112字节占约9.72ms；加最长100字节回复共约18.41ms，能够放进20ms发送时隙。50Hz空闲CRC1约5.47KiB/s。实际速率仍取决于链路、调度与设备，不承诺实车恒定50Hz。

## 本轮验证

- 真实C发送函数 + PC解析器：旧逻辑19/50帧复现；新逻辑50/50帧 +31 GET +5 TSTAT全部交付，1/3/17/112/2048/整块分片均通过。DMA忙不覆写、失败不消费、最长回复、持续TSTAT公平性、文字模式与JustFloat兼容通过。
- CRC专项9项通过，包含3357组逐字节丢失/插入/翻位与分片组合、payload伪回读/伪帧尾、序号回绕/重复/复位、坏包不刷新链路、按设备时间分帧和模式切换。所有损坏测试只交付完整帧的真实坐标。
- 6组核心自检、286项无GUI全量通过；137项界面/串口/协议组合回归、其余60项Qt回归均通过且进程退出0。最后12项专项复核通过（9协议+3地图/刷新），含新增模式切换检查。
- 原GET、真实命令解析、RX恢复、轨迹桥接、RTOS及新发送专项六个硬件脚本均通过。命令提取测试同步补齐现有轨迹参数桩，保留原轴序断言。
- 离线连续供50Hz数据、加载Windows实际字体后，实测遥测/刷新约49.86Hz，事件循环单次最大约8.79ms；地图viewport尺寸在运行中保持不变。该结果是离线压力测试，不是连接车辆测得。
- 最终EIDE构建0错误/0警告，Flash74796B / RAM96936B。

## 生效方法

1. 重启上位机，窗口标题和侧栏应显示v2.1.3。
2. 使用本次生成的`MDK-ARM/build/STM32F407VET6_ILHC/STM32F407VET6_ILHC.hex`更新STM32。
3. 重新连接后，底栏应显示`UART CRC1`，刷新与遥测频率分开显示。若仍为“旧帧(无校验)”，当前板子没有使用CRC1；仅重启PC不会启用本次双端传输修复。

本次未操作正在运行的上位机、未接入COM14、未烧录、未驱动车辆；没有当次原始串口流，未宣称已经完成实车验证。
