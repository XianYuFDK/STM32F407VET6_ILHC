# USART1收发负载核算（2026-10-04）

本记录为当前源码及实际生成报文的离线核算，未连接串口，不代表实测丢包率或实时任务耗时。没有修改波特率或固件。

## 结论

当前115200、8N1的平均带宽足够。应优先关注接收队列、DMA接收重启、应答调度和突发命令，而不是直接提高波特率。
每字节占10个线路位，所以每个方向的理论有效容量为11520字节/秒。TX/RX为独立方向，不把两者负载相加到同一容量。

## 当前通信内容

- USART1：PC调试/轨迹，115200 8N1、TX_RX、无硬件流控；RX/TX均DMA NORMAL。
- 通信任务每20ms至多提交一帧DMA；每帧24个float+4字节帧尾，共100字节。
- 满50Hz遥测为5000字节/秒，占43.4%；单帧线路时间8.68ms。
- 运行状态TSTAT约36字节，周期200ms；PC另以约0.75s周期查询状态。
- 将50Hz遥测与状态、低速参数回复直接相加作保守估算约5250字节/秒，占45.6%。实际代码是应答替换一个遥测时隙，负载低于该叠加估算，实际遥测帧率也低于50Hz。
- PC心跳5Hz，每条PING加换行5字节；低速参数GET为1Hz；轨迹运行查询TSTATUS约1.33Hz。PC到STM32常规运行总负载约65字节/秒，低于1%。
- 新轨迹参数逐项发送并等GET回读，每150ms至多一项，不在运行中下发，平均负载约百余字节/秒。

## 默认860点比赛报文

用当前competition_map、默认任务码、启停区1生成，批次ID取4294967295（最长十位ID）：

- 860个TPOINT，含PC实际发送的单字节换行。
- 每点30～50字节，平均46.7988字节；点表共40247字节。
- 仅点表线路时间最低3.494秒，未计应答等待、头尾命令、GUI及USB调度。
- 每批最多3点，最大连续点表突发150字节；不能把4096点一次压到接收队列。
- MCU每3点产生TSTAT，轨迹应答与遥测时隙交替。持续上传理想应答周期40ms，约75点/秒。
- 该理想点率下PC发送约3510字节/秒，占接收方向30.5%。MCU25Hz遥测+25Hz上传应答约3200～3250字节/秒，占发送方向27.8～28.2%。
- 860点按75点/秒约11.47秒，仅为理想持续上传的时隙估算；实际GUI/USB/串口延迟可进一步延长。满4096点同口径约54.61秒。
- 提高波特率只缩短报文在线路上的时间，不自动提高三点窗口和40ms应答时隙限制。

## 当前需要关注的限制

- 接收环形队列8槽、实际可用7槽，每槽最多256字节，1792字节是所有槽均装满时的上限。短包或碎片会使可用字节容量减少，不能把1792字节当作固定积压容量。
- 通信任务每轮最多处理4个HOST包，收到通知会提前醒来；有剩余包时让出1tick后继续。不是固定每20ms才处理4包。
- RX包超过200ms未被处理、队列满、UART/DMA错误、接收重启失败、命令超过95字符等可能触发错误19。单凭错误19不能确定哪一个子原因。
- PC普通队列每轮最多写16条，虽然轨迹窗口限制为3条，但混入其他命令仍可能形成突发。
- 普通文字应答队列16槽、可用15槽，普通应答优先于遥测。大量连续GET/诊断回复可能降低遥测帧率，即使线路平均带宽没有满。
- 缺少串口错误19子原因的上位机显示、RX队列峰值、TX/RX字节率、DMA重启失败数等在线统计。已有app_rx_overflows和通信任务周期统计只在内存中。

此前截图“车体偏差超过规划裕量”为错误13，由轨迹位置/航向偏差保护触发，不是115200带宽不足的证明。整批路径本地运行，车速提高不需要持续从USART1上传更多轨迹采样。
